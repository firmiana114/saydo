# 相机只读监控面板

并排显示 1 臂手上的 D435i、D405 不固定的全局相机，以及配置了序列号时 2 臂手上的 D435i 的实时彩色画面。支持同时开始、单路/全部停止预览、独立帧率与状态、分别保存当前 JPEG 截图。不访问机械臂或夹爪写入接口，不录制视频。

## 访问与启动

- MSI 本机：`http://127.0.0.1:8088`
- 当前局域网：`http://192.168.101.65:8088`（地址变化时调整）

默认监听 `0.0.0.0:8088`，沿用可信局域网部署，无登录认证。单独访问页面和状态不会打开相机；点击“开始全部预览”或单路“开始预览”后采集。

已有 `.venv` 需包含 `pyrealsense2`、`opencv-python-headless`、`numpy`，系统需提供 `fuser`。在项目根目录执行：

```sh
./scripts/run_camera_monitor.sh --port 8088 \
  --tracker-url http://192.168.101.65:8089
```

`--tracker-url` 必须是当前 8089 实际监听的地址。服务通过本机 owner-only 的 `~/.local/share/saydo-mcp/robot-backend-token` 认证，只读取 `/api/agent/frame`；令牌不进入网页。可用 `--token-file` 指定已有令牌文件。后端无法连接时才尝试直接打开空闲 D435i；认证、身份、时效或其他后端拒绝不会触发设备抢占。

不使用 8089 时可省略 `--tracker-url`，直接采集两台空闲设备。序列号默认读取机器本地 `config/cameras/global.json` 的 `eye_in_hand_serial` 和 D405 的 `serial`；可用 `--eye-in-hand-serial`、`--fixed-serial` 覆盖。没有配置时仅选择唯一匹配型号的设备，多个同型号设备会拒绝猜测。

2 臂手上的相机（2026-10-09 起）：在 `config/cameras/global.json` 里写 `arm2_eye_in_hand_serial`，或启动时加 `--arm2-serial`，页面才出现“2 臂 · D435i 眼在手”这一路（键为 `d435i_arm2`）。8089 接管了 2 臂相机时（2 臂的抓取配置里写了 `camera_serial`）共享 8089 的画面，否则由本服务直接采集。提供这一路时必须同时写明 1 臂相机的序列号，因为两台 D435i 同时连着，不写就无法区分。

默认直接采集 1280×720、15 fps；共享 8089 时显示其实际原始图像尺寸（当前 640×360），不冒充原生全分辨率。状态栏显示序列号、机位和画面来源。`--width`、`--height`、`--fps` 控制本服务直接采集的流。

## 相机共用与释放

- 每台相机独立管理采集线程，最多四个观看连接共用一路采集。单路异常不关闭另一台。
- D435i 已由 8089 使用时读取其最新原始画面，不开启第二条 SDK pipeline，也不暂停或重启 8089。释放共享预览只关闭本页连接，8089 继续采集。
- D405 预览与现有全局观察共用同一设备锁。预览运行时，`observe_global` 的短进程从监控服务获取请求之后的新帧，保留身份、时间和“仅观察、未经基座标定”的约束；没有活动预览时，2026-10-10 起也由本服务打开相机给出画面（观察结束几秒后自行释放）；只有本服务没有运行时才沿用原独立采集流程。已有执行器无需重启。
- 最后一个观看者关闭后，没有程序在取图的相机自动关闭。页面上的“停止预览”“停止全部预览”（2026-10-10 前叫“释放”）结束对应的预览连接；相机是预览和取图程序共用的，还有程序在取图时相机继续采集，程序不受影响。
- **借用与归还**：手眼采集程序需要某台相机时，向本服务“借用”：本服务停止这一路并在一段时间内（最长 60 秒）拒绝新的预览连接，采集结束后采集程序归还。页面看到相机被借走时收起画面并说明原因，归还后自动重连，不用手动释放或重新开始。为什么要拒绝连接而不只是暂停：页面会自动重连，只暂停的话重连会在采集开始前把相机又占回去。只有“借走再归还”才自动重连；出错或被别处释放后仍由用户决定是否重新开始。
- **程序向本服务要画面（2026-10-10 起，完整说明见下一节）**：一台相机同一时刻只能被一个进程打开。程序如果自己去打开相机，预览就得让出来，操作者摆放物品时看不到画面。所以需要全局相机画面的程序改为向本服务取图：`GET /api/cameras/<id>/frame?keep_s=20&format=png`。带 `keep_s` 时，相机没开就由本服务打开，并至少再保持采集这么多秒（上限 60）；程序每取一次续一次，退出后不用归还，期限一到、又没有人看预览，相机自行释放。`format=png` 给出无损图像（每个像素与相机给出的相同），应答里的 `intrinsics` 是这路彩色画面的内参与畸变参数。预览和程序共用同一次打开的相机，互不影响。全局相机的快速标定（`saydo/calibration/global_camera.py`）走的就是这条路。与“借用”的区别：借用是把相机整台让给另一个进程，期间没有预览；取图是相机留在本服务手里，预览照常。手上相机转接的是 8089 的画面，没有无损图像和内参，这类程序应直接向 8089 取。
- 本服务不抢占其他程序、不复位设备。两路图像独立采集，不具备同步标定样本或深度采集能力。

## 作为相机服务：向其他程序提供画面（2026-10-10 起）

本服务正在从“预览页面”扩成全项目的相机服务：相机统一由它打开，别的程序向它要画面。原因是一台相机同一时刻只能被一个进程打开，各程序自己去开就得互相借来借去，借走期间预览没有画面。目前已接入的是全局相机 D405；两台手上相机仍由 8089 打开，本服务转接它的画面（迁移是下一步）。

取画面有两条路，按用途选：

| 路 | 适合 | 给出什么 | 速度 |
| --- | --- | --- | --- |
| 网页接口 `GET /api/cameras/<id>/frame?keep_s=…` | 每秒取一两次的程序：标定、大模型的全局观察 | 彩色图，JPEG 或无损 PNG（`format=png`），连同内参与畸变参数 | 一次约 0.1 秒 |
| 共享内存，经 `saydo/contracts/camera_frames.py` 的 `Feed` | 要连续原始画面的程序：定位与跟踪 | 未压缩的彩色图和已对齐到彩色图的深度图、内参、曝光时刻 | 相机出一帧约 2 毫秒后可读到，读一帧约 0.3 毫秒 |

共享内存（shared memory）是两个进程都能读写的同一块内存，这里是 `/dev/shm/saydo-camera-<id>` 文件。本服务每出一帧就写进去，取图程序把它映射进自己的地址空间直接读，不经过网络。读写不加锁，靠一个计数器保证读到的是完整的一帧（写之前、写完各加一，读的一方前后各看一次，不一致就重读）。排布与读写代码都在 `saydo/contracts/camera_frames.py`，相机服务和取图程序必须是同一版代码。

两条路共用同一套“保持采集”的规则：

- 程序每次取图（或 `Feed` 每隔几秒）告诉本服务“我还在用”，带上要再保持多少秒（上限 60）。相机没开时由本服务打开，约两秒出第一帧。
- 程序退出后不用归还。期限一到、又没有人在看预览，本服务自行释放相机。
- 预览和各个程序共用同一次打开的相机，互不影响。页面上点“停止预览”只结束预览，不打断正在取图的程序。相机因故重新打开过（停帧恢复失败后被程序重新打开等）时，`Feed` 会自动接上新的共享内存。
- 相机被“借用”（见上）期间，取图请求会被拒绝并说明原因。

**深度图默认不采集，共享内存里只有彩色图**（`depth_raw` 为 None）。启动时加 `--global-depth` 才同时开彩色和深度两路（都是 1280×720、15 帧/秒），深度图逐像素对齐到彩色图后写入共享内存。默认关掉的原因见下面的“深度图与丢帧”。D405 的彩色画面带畸变参数（驱动里叫 Inverse Brown Conrady；2026-10-10 用驱动自带的投影函数核对过，这组系数的用法与 OpenCV 的畸变模型一致，直接传给 OpenCV 即可），对齐后的深度图与带畸变的彩色图逐像素对应，使用时两者要一起去畸变。

实测（2026-10-10，MSI，真实 D405，开着深度图，取图程序用 8089 的 Python 环境，每次只测几秒）：稳定时 14.9 帧/秒；从曝光到程序读到中位 28 毫秒、最大 45 毫秒，其中本服务写入到程序读到约 2 毫秒；读一帧 0.34 毫秒。这些数字说明的是“服务到程序”这一段够快；相机到电脑这一段开着深度图时并不稳定，见下。

### 深度图与丢帧（2026-10-10）

开着深度图部署后，用户标定时 D405 的预览每隔一分钟左右就消失。直接读相机各 100 秒对比（当时 8089 正在用两台手上相机）：

| 配置 | 实际帧率 | 丢帧 | 最长停顿 |
| --- | --- | --- | --- |
| 彩色 + 深度，都是 1280×720、15 帧/秒 | 9.1 帧/秒 | 约 37% | 14.1 秒 |
| 只有彩色 1280×720、15 帧/秒 | 14.6 帧/秒 | 约 2% | 0.2 秒 |

三台相机和 2 臂的 USB 网卡接在同一个 USB 集线器上（集线器到电脑是 5 Gbps），推测是这条线路带不动；没有换接法验证过。当时本服务等一帧超过 3 秒就结束采集，页面随之断开，而标定脚本下一秒又把相机打开，页面却不会自己接回去，所以看起来像“卡死”。几秒钟的测速没有碰上长停顿，没能发现这个问题。

**换接法后的复测（2026-10-10 15:10）**：用户把 D405 从集线器上拔下，直接插到电脑的另一个 USB 口（`lsusb -t` 显示它在 Bus 002 Port 001，5000M，即 USB 3；两台手上相机和 USB 网卡仍在 Port 002 的集线器上）。同样条件下直接读相机：

| 配置 | 时长 | 实际帧率 | 丢帧 | 最长停顿 |
| --- | --- | --- | --- | --- |
| 彩色 + 深度，都是 1280×720、15 帧/秒 | 120 秒 | 14.9 帧/秒 | 0 | 0.07 秒 |
| 只有彩色 | 60 秒 | 14.9 帧/秒 | 0 | 0.07 秒 |

结论：丢帧是集线器那条线路带不动造成的，D405 单独一个口就没有问题。**D405 必须保持单独接在电脑的 USB 3 口上。**

尚未打开深度图（服务仍按默认启动）。打开前还要查一件事：复测期间 15:12:16 两台手上相机的预览同时因“8089 给出的画面超过一秒”而结束。只出现这一次，原因未查明（可能是 8089 当时忙，也可能是 D405 满负荷时挤占了手上相机的传输）。手上相机关系到抓取，所以要在 D405 开着深度图连续运行几分钟的同时，盯着两台手上相机的出图间隔，确认不受影响，再把 `--global-depth` 加进启动命令。

对策：

- 深度图默认不采集。要用 D405 的深度（定位与跟踪）之前，先解决线路问题：把 D405 单独接到电脑的另一个 USB 3 口再测，或降低分辨率、帧率。
- 相机停帧时不再结束采集：等一帧超时就重开采集，最多连续 5 次，观看连接和取图程序都留着，恢复后接着用。期间状态仍是“实时采集中”，`stalled` 为真，页面显示“相机已有 N 秒没有出图，服务正在等它恢复”。日志各记一行“重开采集”和“恢复出图”。
- 页面：用户想看的一路因出错断开后，只要相机又在采集（例如被取图程序重新打开），页面自动接回；相机空闲时不自动打开。

取图程序的写法（不需要相机驱动）：

```python
from saydo.contracts import camera_frames

feed = camera_frames.Feed('http://127.0.0.1:8088', 'd405')
frame = feed.frame()          # 等一帧比上次更新的画面
frame['bgr']                  # 彩色图，1280×720
frame['depth_raw'] * frame['depth_scale_m']   # 深度，单位米
frame['K'], frame['distortion']               # 内参与畸变
frame['captured_at']          # 曝光时刻
```

取不到时抛出 `camera_frames.CameraUnavailable`，异常信息写明原因（相机服务没有运行、相机打不开、相机被借走等）。

## HTTP 接口

| 接口 | 行为 |
| --- | --- |
| `GET /api/status` | 聚合状态及 `cameras.d435i`、`cameras.d405`（配置了时还有 `cameras.d435i_arm2`）；每路含 `arm` 和 `held_s`（还要借出多少秒）；保留旧顶层字段 |
| `GET /stream/d435i`、`GET /stream/d405` | 开始/加入对应 MJPEG 预览 |
| `GET /snapshot/d435i.jpg`、`GET /snapshot/d405.jpg` | 当前新鲜 JPEG，无活动预览或图像过期时 409 |
| `GET /api/cameras/<id>/status` | 单路状态；`kept_s` 是程序要求再保持采集多少秒，`intrinsics` 是本服务直接采集时的内参与畸变 |
| `POST /api/cameras/<id>/pause` | 停止单路预览：结束预览连接，没有程序在取图时同时关闭相机；请求体带 `{"hold_s": 秒数}` 时是借出这台相机，一定关闭 |
| `POST /api/cameras/<id>/resume` | 提前归还借出的相机 |
| `POST /api/cameras/<id>/keep` | 请求体 `{"keep_s": 秒数}`：应取图程序的要求保持采集，必要时打开相机，等它出图后返回这一路的状态；状态里的 `shared_frames` 是原始画面所在共享内存的路径和标识 |
| `GET /api/cameras/<id>/frame` | 等待请求之后的新帧并返回带身份/时间的 JPEG JSON；不带参数时不会启动设备 |
| `GET /api/cameras/<id>/frame?keep_s=秒数` | 同上，但相机没开时先打开，并至少再保持采集这么多秒；可再加 `format=png` 取无损图像 |
| `POST /api/pause` | 停止全部预览（不借出；有程序在取图的相机继续采集），兼容原标定及 8089 启动协调 |

旧 `GET /stream`、`GET /snapshot.jpg` 仍指向 D435i。前台 Ctrl-C 或服务 SIGTERM 只结束本服务采集与连接，不停止机器人、不关闭 8089。

后台实例的 PID 和日志沿用 `work/camera_monitor/server.pid`、`work/camera_monitor/server.log`；不配置开机启动。
