# 机械臂与桌面、立杆、另一台臂的碰撞检查

本文说明程序怎样判断一次动作会不会让机械臂或夹爪碰到桌面、桌上的立杆和另一台机械臂：检查了什么、没检查什么、数据从哪来，以及后续几个阶段的安排。

## 为什么需要

逆解（由夹爪的目标位置反算各关节角度）和路径检查原先只看夹爪参考点这一个点。手肘、前臂、手腕和夹爪本体占多大地方，桌上立着一根装全局相机的杆子，程序都不知道。RM75 有 7 个关节，同一个夹爪位置对应很多种手臂摆法，逆解完全可能挑中手肘伸向立杆的那一种。

2026-10-09 的回放说明了这一点：当天 15:35 那次 1 臂实机抓放，按实际下发的关节角计算，肘部和前臂在调姿到入孔的过程中经过了立杆现在所在的位置（模型算出的间距最小为 −69 毫米，即重叠）。用户确认那次确实把立杆碰倒了。这个方案在加入本检查后会被拒绝。

## 检查什么

| 对象 | 规则 |
| --- | --- |
| 立杆 | 机械臂各段和夹爪离立杆表面至少 30 毫米（用户指定） |
| 桌面 | 肩部以上的各段和夹爪不得低于桌面，不留余量；底座和肩部固定在桌面上方，不检查 |
| 另一台机械臂 | 两臂的各段和夹爪之间至少 30 毫米（缺省值，可改）。它静止时按当前姿态算，正在执行动作时按它即将要走的整条路径算，见“阶段四”一节 |

**没有检查的**（用户决定或尚未实现）：夹爪上的相机和支架、被夹着的物品、桌上的其他物品、全局相机本体。夹爪上的相机不在模型里，意味着“相机先碰到桌面”这类情况本检查拦不住。那次事故的源头——物品被画面裁掉导致方向认反——由定位阶段的出画检查来防，见 [`scene_snapshots.md`](scene_snapshots.md) 的“出画检查”一节。

## 外形怎么表示

每一段用一个胶囊体（capsule）表示：一条线段加一个半径，也就是两头是半球的圆柱。它算距离简单，又能把手臂的一段包住。定义在 `saydo/robot/collision_model.py`。

| 部分 | 数量 | 尺寸来源 |
| --- | --- | --- |
| 机械臂（底座加 7 个连杆） | 8 个，半径 39～74 毫米 | 厂家模型文件 `rm_description/meshes/rm_75_arm/*.STL` 逐段拟合，另加 1 毫米 |
| 夹爪 | 5 个 | 知行 CTAG2F90D 产品外形图 |

夹爪外形图上的关键尺寸：

| 尺寸 | 数值 |
| --- | --- |
| 闭合总长（安装面到指尖） | 222.5 毫米 |
| 张到最大时的总长 | 205 毫米（指尖缩回 17.5 毫米） |
| 张到最大时的总宽 | 151 毫米 |
| 行程（两指内侧间距） | 90 毫米 |
| 本体厚度 | 45 毫米 |
| 指垫宽度 | 23 毫米 |
| 安装座直径 | 75 毫米 |

这款夹爪是连杆式的，两指沿弧线开合：张开时指尖缩回、整体变宽。模型取“任何开度下都包得住”的范围，所以不随开度变化，偏保守。闭合指尖那个胶囊体的末端球面正好落在夹爪参考点上，因此竖直向下抓取时指尖贴近桌面不会被误判；夹爪放平或倾斜着靠近桌面时，本体和张开的手指的宽度会被算进去。

运动学参数（各连杆的位置怎么由关节角算出）与厂家模型逐连杆核对过，相差小于 0.02 毫米；与控制器读回的夹爪位置相差约 0.2 毫米。

## 什么时候检查

所有动作在规划时都经过同一个入口 `motion_validation.check_waypoints`。检查在两处进行，用的是同一套外形和算法：

- **逆解搜索的过程中**（2026-10-10 起）：离线检查器为每个路点挑选手肘摆法时，就排除会碰到桌面或立杆的姿态和途中会碰撞的走法，所以它能主动换一种摆法绕开，而不是只能否决。见 [`arm_angle_ik.md`](arm_angle_ik.md)。
- **逆解完成之后**：对找到的那条路径再完整核对一遍，这一遍是最终放行的依据。步骤如下：


1. 把“当前关节角 → 第 1 个路点 → 第 2 个路点 → …”连成一条路径。
2. 相邻两点之间按关节角直线取样，任一关节每转 2 度取一个姿态。
3. 每个姿态算出全部胶囊体的位置，逐个比较离立杆和桌面的距离。
4. 有一处不满足就否决这个方案，报错写明是哪一段、走向哪个路点、差多少；有候选方案的流程会自动试下一个。

覆盖的动作：页面上的抓取、桌面放置、调姿、持物移动、固定抓放。复位是直接转到目标关节角，在发令前单独检查这一条路径，不通过时提示先手动把机械臂移到空旷处。

每次检查的结果（检查了多少个姿态、全程离立杆、桌面和另一台臂最近多少、最近的是哪一段）写在任务记录的 `collision_check` 里。

当前姿态本身不判：机械臂已经在那里，不是计划的一部分。但如果它已经在立杆的余量之内，离开的头几个取样点通常也在余量内，方案仍会被否决，需要手动移开。

## 障碍物数据

桌面高度取各臂抓取配置里的 `table_z_m`。立杆写在各机器本地的 `config/calibration/workspace_obstacles.yaml`（不入 Git）：

```yaml
schema_version: 1
pole:
  shape: vertical_square_bar
  side_m: 0.02        # 截面边长
  margin_m: 0.03      # 要求的最小间距
  position_m:         # 立杆中心，在各臂自己的基座坐标系里
    arm1: [-0.0782, -0.2633]
    arm2: [0.0740, -0.2442]
```

没有这个文件，或文件里没有某台臂的位置时，那台臂只检查桌面。立杆高度按无穷处理，方杆按外接圆（半径为边长的 0.707 倍）处理。

立杆位置的测法（2026-10-09）：让两只夹爪从相反方向夹住立杆，只读读取两臂位姿，取两指尖之间的中点。两臂各算一次，换到同一坐标后相差 6.6 毫米，取平均。记录在 `work/calibration/pole_touch_20261009.json`。**立杆被挪动过就要重新测。**

| 局限 | 影响 |

| 页面抓取退回 `movel` 的直线段按两端之间的关节角直线来检查 | 控制器实际的手肘摆法可能不同。其余直线段都已改为逐点关节运动，见“直线段改为逐点关节运动”一节 |

## 阶段二：关节段不再让控制器自己选手臂摆法

**要解决的问题**：阶段一检查的是“程序自己算出来的那条路径”。但页面抓取的预抓点、桌面放置的抬升和转移这三段，原先发给控制器的是 `movej_p`（位姿关节运动）：只告诉它夹爪要到哪、朝哪，七个关节各转多少由控制器自己定。RM75 有 7 个关节，比确定夹爪位姿所需的 6 个多一个，同一个夹爪位姿对应无穷多种手肘摆法，控制器选哪一种我们事先不知道。于是检查的路径和实际走的路径可能不是同一条。

**怎么改的**：这三段改成发 `movej`（关节运动），目标是程序的逆解刚刚算出、并通过了碰撞检查的那组关节角。`movej` 是各关节同步转到给定角度，路径就是关节角空间里的直线，正是检查时取样的那一条。到位后除了核对夹爪位姿，还核对实际关节角与目标相差不超过 0.5 度。

| 动作 | 段 | 原来 | 现在 |
| --- | --- | --- | --- |
| 页面抓取 | 到预抓点 | `movej_p` | `movej` 到已检查的关节角 |
| 页面抓取 | 接近、抬升 | `movel` | 当时不变；后来改为逐点关节运动，见下文 |
| 桌面放置 | 抬升、转移 | `movej_p` | `movej` 到已检查的关节角 |
| 桌面放置 | 下降、后撤、退出 | `movel` | 当时不变；后来改为逐点关节运动，见下文 |
| 调姿、持物移动、固定抓放、复位 | 全部 | 本来就不用 `movej_p` | 不变 |

页面抓取每段发令前的重查，也从“只查眼前这一个路点”改为“查从这一段起剩余的全部路点”，这样选出的手臂摆法与规划时一致，后面够不到也能在靠近物品之前发现。

**改动有多大（离线回放的结果，2026-10-10）**：拿 MSI 上 24 次带完整记录的历史页面抓取比较“控制器当时自己选的预抓点关节角”和“程序算出的关节角”。22 次相差不到 0.1 度，即这 22 次改不改走的是同一条路；另外 2 次相差 6.3 度和 13.5 度，这正是要消除的不确定性。

**一个试过又撤掉的做法**：原计划顺带让页面抓取的接近和抬升两段沿直线每 10 毫米取样检查（固定抓放就是这样做的）。用真实的逆解检查器回放 63 次历史页面抓取，取样检查拒绝了其中 7 次，而这 7 次里有 5 次当时由控制器的 `movel` 实际执行成功。也就是说，“相邻取样点的关节解变化不超过 10 度”这条要求比控制器的实际能力更严，照搬过来会平白缩小页面抓取的可抓范围。所以页面抓取的直线段仍只检查两端。固定抓放不同：它的直线段是程序沿取样点逐点发关节运动，必须逐点有解。

**没有做的**：原计划里的“转移走安全高度”没有新增路点。现有流程已经是先抬升（抓取后抬 20 厘米、放置前到释放点上方）再平移再下降；关节段现在走的就是检查过的路径，不通过会在规划时被否决。

**当时留下的缺口**：`movel` 直线段的手肘摆法还是控制器说了算。2026-10-10 已按“像固定抓放那样改成逐点关节运动”处理，见“直线段改为逐点关节运动”一节。

**验证状态**：自动测试通过；上面的离线回放用的是真实逆解检查器和历史记录。**没有在真实机械臂上执行过**，首次实机抓取和放置时请留意预抓点和转移这两步的手臂姿态。

## 阶段四：两台臂互相避让

**要解决的问题**：两台臂的底座只相距约 0.52 米，工作范围大片重叠。此前每台臂规划时只知道桌面和立杆，不知道另一台臂在哪里。

**做法**：把另一台臂也当作障碍物，用的仍是同一套胶囊体。分两种情况：

| 另一台臂的状态 | 把什么当作障碍物 | 数据从哪来 |
| --- | --- | --- |
| 没有在执行动作 | 它当前姿态下的 13 个胶囊体 | 向它的控制器只读查询关节角，半秒内的读数可以沿用 |
| 正在执行动作 | 它“从当前位置起即将要走的路径”扫过的空间，称为**占位** | 它每一段运动发令之前登记在程序里 |

两种情况都要求本臂与它之间至少留 30 毫米。坐标用两底座的相对位置（`config/calibration/base_relation.yaml`）换到本臂的基座坐标系。

**占位互斥是什么意思**：一台臂在发令之前，先检查自己即将要走的路径不进入另一台臂占着的空间，通过后把这条路径扫过的空间登记为自己的占位。另一台臂此后规划和发令都不得进入。两臂各自的占位互不重叠，所以不论谁先走到哪里都不会相撞。这样做绕开了一个缺口：程序只知道路径，不知道机械臂什么时刻走到哪里。代价是偏保守，时间上本来错得开的两条路径也会被拒绝。

```text
1 臂发令前：  取占位版本号 → 读取 2 臂占着的空间 → 检查自己的路径
                  │ 通过
                  ▼
              登记自己的占位（版本号没变才登记成功；变了就按新的占位重查，最多 3 次）
                  │
                  ▼
              发出这一段的运动指令 …… 任务结束时撤销占位
```

几个细节：

- **什么时候登记**：任务进行中、每一段运动发令前的那次路径复核（`verify_motion_targets`）通过之后。固定抓放和页面抓取复核的是剩余的整条路径，所以占位是整条剩余路径；桌面放置、调姿、持物移动每次只复核下一段，占位就是下一段。复位在检查通过后登记“当前姿态到目标姿态”这一条。
- **什么时候撤销**：任务开始和结束时（`busy` 状态改变）。撤销后另一台臂按“读取当前关节角”对待它。
- **占位怎么表示**：路径按每 2 度取一个姿态，每个姿态 13 个胶囊体。同一段手臂在相邻姿态下几乎重合的合并成一个并加粗，总数不超过 96 个；结果只会比真实扫过的空间大。
- **搜索时也避让**：另一台臂占着的胶囊体随每次请求传给离线检查器，它在挑选手肘摆法时就排除会碰到另一台臂的摆法（见 [`arm_angle_ik.md`](arm_angle_ik.md)）。
- **规划进行中另一台臂动了**：规划用的是开始时取的一份。等到真正发令前的复核，用的是当时最新的占位；冲突的话在这里被拒绝，不会发出运动。

**读不到另一台臂时**：缺省拒绝规划，并提示原因。它断电并且确认停在碰不到的地方时，可以在障碍物文件里改成忽略：

```yaml
other_arm:
  margin_m: 0.03            # 两臂之间至少要留的距离，缺省 0.03
  when_unreadable: refuse   # 读不到另一台臂时：refuse 拒绝（缺省），ignore 忽略
```

本机没有两底座相对位置的文件，或只配置了一台臂时，不做这项检查。

**没有覆盖的情况**：

| 情况 | 说明 |
| --- | --- |
| 绕过 8089 直接指挥机械臂的程序，或用示教器手动移动机械臂 | 不会登记占位。另一台臂只能靠读取关节角看到它，看到的是读取那一刻的姿态，最多滞后半秒 |
| 被夹着的物品、夹爪上的相机 | 不在外形模型里，靠 30 毫米余量兜底 |
| 页面抓取退回 `movel` 的那一段 | 手肘怎么摆由控制器决定，占位按两端关节解之间的关节角直线估算 |

**验证状态**：自动测试通过；2026-10-10 用两台臂的真实关节角做了只读核对（两臂都在观测姿态时相距 325 毫米，从两边各算一次结果一致），并带上 2 臂的当前姿态回放最近 16 次 1 臂历史方案（15 次找到方案，全程离 2 臂 64～230 毫米；1 次被判为无法完成）。**没有在真实机械臂上执行过，更没有试过两臂同时运动。**

## 直线段改为逐点关节运动（2026-10-10）

阶段二留下的缺口是 `movel`：它的手肘摆法由控制器决定。现在各动作的直线段都改成沿取样点逐点关节运动，目标是刚检查过的关节解：

| 动作 | 直线段 | 现在 |
| --- | --- | --- |
| 页面抓取 | 接近、抬升 | 每 10 毫米一个取样点，逐点关节运动。**找不到连续的关节解时退回 `movel`**，记在任务记录的 `linear_fallbacks` 里并写一条警告日志 |
| 桌面放置 | 下降、后撤、退出 | 沿原来就在检查的取样点逐点关节运动；找不到连续解时和原来一样拒绝，不退回 |
| 持物移动（非固定方案） | 直线路径 | 同上 |
| 固定抓放 | 全部 | 本来就是逐点关节运动 |

页面抓取保留退回的原因见上一节“一个试过又撤掉的做法”：沿线取样检查曾拒绝过控制器实际能走的直线。改用按臂角求逆解之后这种情况应当少得多，但没有重新统计。

代价是一步一停：每个取样点到位后才发下一个，直线段会比 `movel` 慢，动作不连贯。**没有实机验证。**
