# SayDo 编码规范

本规范的首要目的：让没有参与过编写的工程师能读懂代码。适用于本仓库全部自写代码，
读者包括人类工程师和 AI 代理（Codex、Claude 等）。

- 生效日期：2026-10-08。
- 不适用：`third_party/` 与 `ros2_rm_ws/src/` 下的第三方源码快照，保持上游原样。
- 改代码之前先读本文件；提交之前运行第 10 节的自检脚本。

## 1. 优先级

规则冲突时，按下面的顺序取靠前的一项：

1. 本文件写明的规则（含第 3 节的例外和第 5 节的追加规则）。
2. Google 各语言风格指南（第 2 节）。
3. 所在文件周边代码的现有写法。

第 3 项排在最后是有意的：仓库里有大量早于本规范的旧代码，**不得以“与周边旧代码保持
一致”为由沿用不合规的写法**。旧代码如何处理见第 9 节。

## 2. 基线：Google 风格指南

下表各指南的条款于 2026-10-08 对照官方原文核对。本文件第 4～8 节用中文写出日常
最常用的条款，未写到的情形以原文为准。

| 语言 | 指南 | 原文 |
| --- | --- | --- |
| Python | Google Python Style Guide | <https://google.github.io/styleguide/pyguide.html> |
| JavaScript | Google JavaScript Style Guide | <https://google.github.io/styleguide/jsguide.html> |
| HTML/CSS | Google HTML/CSS Style Guide | <https://google.github.io/styleguide/htmlcssguide.html> |
| C++ | Google C++ Style Guide | <https://google.github.io/styleguide/cppguide.html> |
| Shell | Google Shell Style Guide | <https://google.github.io/styleguide/shellguide.html> |

## 3. 对 Google 规范的例外

| 条款 | Google 的要求 | 本项目的做法 | 理由 |
| --- | --- | --- | --- |
| 检查与排版工具 | Python 运行 pylint，建议用自动排版工具 | 不引入第三方工具，改用 `tools/style_check.py`（仅标准库） | 项目约定非必需不引入依赖 |
| JavaScript 模块 | 新文件用 ES 模块（`import`/`export`） | 沿用 `<script>` 标签加载的普通脚本 | 改加载方式要同时改页面与全部前端测试，与可读性关系不大 |
| C++ 异常 | 禁用异常 | 允许 | 该条是 Google 为兼容自家旧代码而定；逆解检查器是独立小程序 |
| 许可证头 | 每个文件带许可证声明 | 不加 | 私有仓库，无对外许可证 |
| 行宽的计量 | 80 个字符 | 80 列显示宽度，一个汉字或全角符号算 2 列 | 注释和提示是中文，按字符数计会出现实际 160 列宽的行 |
| 同行语句 | 允许不带 `else` 的 `if x: 语句` 写在一行 | 一律换行 | 规则更简单，机器可检查 |

## 4. 通用规则（所有语言）

- 文件编码 UTF-8，缩进用空格，不用制表符，行尾不留空白。
- 行宽不超过 80 列。例外：导入语句、含网址的行、无法断开的长字符串常量、
  Markdown 文档、HTML 标记。
- 一行只写一条语句。
- **标识符用英文，注释、文档字符串、面向操作者的提示用中文。**
- 标识符写完整单词，不自造缩写。允许的短名：循环计数 `i`、`j`、`k`，坐标 `x`、`y`、
  `z`，以及第 5.2 节的坐标系写法。
- 注释写“为什么”，不复述代码在做什么。踩过的坑、反直觉的取舍、数值的来历必须写。
  例：为什么固定抓放不用控制器的直线运动。
- 待办写成 `TODO: 说明`，说明里写清触发条件或相关记录的位置。

## 5. 本项目追加规则

这一节是 Google 指南没有、但本项目的领域需要的约定。

### 5.1 单位后缀

带量纲的变量、参数、配置项、字典键，名字必须以单位结尾。

| 量 | 后缀 | 例 |
| --- | --- | --- |
| 长度（米 / 毫米） | `_m` / `_mm` | `lift_height_m`、`release_gap_m` |
| 角度（度 / 弧度） | `_deg` / `_rad` | `target_rpy_deg`、`max_joint_step_deg` |
| 时间（秒 / 毫秒） | `_s` / `_ms` | `timeout_s` |
| 比例（百分比） | `_percent` | `arm_speed_percent` |
| 图像（像素） | `_px` | `reprojection_rms_px` |

内部计算统一用米、弧度、秒；度和毫米只出现在配置、接口和给人看的文字里。在两种
单位之间换算的那一行必须能从变量名看出换算方向。

### 5.2 坐标系与变换

- 4×4 齐次变换矩阵命名为 `<参照系>_T_<对象>`，读作“对象在参照系里的位姿”。
  例：`base_T_object` 是物品在机械臂基座坐标系里的位姿。
- 连乘时相邻下标必须相同，写错一眼可见：
  `base_T_object = base_T_flange @ flange_T_camera @ camera_T_object`。
- 点和向量把所在坐标系写在量纲之前：`grasp_point_object_m`、`retreat_vector_base_m`。
- 仓库里已有的坐标系名：`base`（基座）、`flange`（法兰，机械臂末端安装面）、
  `tcp` / `grip_tcp`（夹爪中心）、`camera` / `color_optical_camera`（相机）、
  `object`（物品）、`feature`（物品上的特征点）、`board`（标定板）。新增坐标系须
  先在这里登记。

### 5.3 会让机械臂或夹爪动作的代码

- 只有以 `writes=True` 创建的 `RobotClient` 能发送写入指令。规划、查询、离线回放、
  测试一律用 `writes=False`。
- 会发送运动或夹爪指令的函数，文档字符串的第一段必须写明“会发送运动指令”或
  “会发送夹爪指令”。
- 这类函数的返回值或诊断记录必须如实填写 `motion_sent`，包括失败的情况。
- 新增接口应当把只读规划和真实执行分成两个函数，不用一个布尔参数在同一个函数里切换。
- 与安全有关的数值（容差、时限、速度、步长）必须是带单位后缀的具名常量或配置项，
  旁边注释取值依据，不得写成散落在表达式里的数字。
- 文档、测试、连通性排查不得触发使能、点动、复位、抓取或夹爪动作（同 `AGENTS.md`）。

### 5.4 路径与配置

- 禁止 `sys.path.insert` / `sys.path.append`。跨目录引用一律用从项目根开始的完整包名。
- 禁止写死 `/home/pc/...` 等机器相关的绝对路径。
- 项目根目录、`work/`、`config/` 下的路径只从一个公共模块取（结构重构阶段建立；
  在它建立之前，旧代码里的 `ROOT = ...parents[2]` 写法暂时保留，不新增）。
- 与某个物品绑定的数据只放 `work/object_models/<物品ID>/`（同 `AGENTS.md`）。

### 5.5 错误信息与日志

- 报错写明对象和实际数值。
  反例：`位姿变化过大`。正例：`tube 同帧细化位姿变化 7.2 毫米，上限 5 毫米`。
- 处理异常时保留原始异常链（`raise ... from error`）；善后代码不得抛出新的异常
  盖住原始错误。
- 日志用项目已有的 `logging` 写法，默认级别不低于 INFO；不记录口令、令牌和大体积
  原始数据。
- 日志调用传格式串和参数（`LOG.info('已启动，进程号 %d', pid)`），不传 f-string。

### 5.6 测试

- 测试替身只放在系统边界：控制器通信、相机、大模型接口、子进程、时钟。
- **不得把被测流程里的整个阶段替换成假函数。** 每条执行路径至少要有一个测试走过
  真实的流程代码。（教训：固定抓放的放置阶段曾被整体替换，三处缺陷直到实机才暴露。）
- 测试函数名写明被验证的行为：`test_stops_before_motion_when_path_unsolvable`。
- 测试文件不强制文档字符串和类型标注，其余规则照常适用。

## 6. Python

### 6.1 排版

- 缩进 4 个空格。折行用括号内的隐式续行，不用反斜杠。
- 不用分号；`if`、`for`、`while`、`with`、`try`、`def`、`class` 的语句体一律另起一行。
- 顶层定义之间空两行，方法之间空一行。
- 运算符两侧、逗号之后留一个空格；关键字参数的 `=` 两侧不留。
- 字符串用单引号，文档字符串用三个双引号。拼接用 f-string，不用 `+`。
- 多行的括号内容，最后一项后面加逗号，右括号独占一行。

### 6.2 导入

- **只导入模块和包，不直接导入函数、类、常量。** 调用处写成 `模块.名字`，读者不用
  翻到文件开头就知道它来自哪里。

  ```python
  import pathlib                      # 合规
  from tools.task_runner import config  # 合规：config 是模块
  from pathlib import Path            # 不合规：Path 是类
  ```

- 例外：`typing`、`collections.abc`、`typing_extensions`、`__future__` 可以直接导入
  其中的名字。
- 不用相对导入（`from . import x`），写完整包名。
- `import x as y` 只用于公认的缩写，如 `import numpy as np`。
- 每行一个导入。分组顺序：`__future__`、标准库、第三方库、本项目；组内按字母排序。

### 6.3 命名

| 对象 | 写法 | 例 |
| --- | --- | --- |
| 模块、包 | `lower_with_under` | `grasp_geometry` |
| 类、异常 | `CapWords` | `RobotClient` |
| 函数、方法、参数、变量 | `lower_with_under` | `plan_release` |
| 模块级常量 | `CAPS_WITH_UNDER` | `MAX_COLUMNS` |
| 仅模块或类内部使用 | 加前缀 `_` | `_request` |

名字里不带类型（不写 `slot_list`、`config_dict`）。由外部库规定的名字不受此限，
例如 `http.server` 的 `do_GET`、`unittest` 的 `setUp`。

### 6.4 文档字符串

- 每个模块以文档字符串开头，说明它负责整条链路中的哪一段、不负责什么。
- 每个公开的函数、方法、类必须有文档字符串。公开指名字不以 `_` 开头。
- 首行是一句话摘要，以句号结尾，不超过 80 列；需要展开时空一行再写。
- 小标题 `Args:`、`Returns:`、`Raises:`、`Attributes:` 保留英文，内容写中文。
  参数说明里写清含义、单位、坐标系。

```python
def descent_side_offset_m(depth_m: float, tilt_deg: float) -> float:
    """计算竖直下降时试管相对孔中心的横向偏移。

    机械臂沿基座竖直方向下降，孔的轴线却随试管架一起倾斜，
    所以下降越深偏得越多。

    Args:
        depth_m: 下降深度，单位米。
        tilt_deg: 试管架 Z 轴偏离竖直方向的角度，单位度。

    Returns:
        孔口处的横向偏移，单位米。

    Raises:
        ValueError: 下降深度为负数。
    """
```

### 6.5 类型标注

- 公开函数和方法的全部参数与返回值必须标注。内部函数在新增和改动时标注。
- 跨模块传递的字典（方案、场景、夹持记录等）定义成 `typing.TypedDict` 或
  `dataclasses.dataclass`，并逐字段说明含义和单位。
- 需要兼容 Python 3.9 的文件在开头写 `from __future__ import annotations`。

### 6.6 规模

- 函数超过约 40 行时，考虑能否在不破坏结构的前提下拆开。这是提醒，不是硬性上限。
- 文件超过约 500 行时，考虑是否承担了不止一项职责。（本项目的参考线，非 Google 条款。）
- 一个函数只做一件事；先写出“这段在解决什么问题”，再决定拆不拆。

### 6.7 异常

- 不写裸的 `except:`。
- 不捕获 `Exception`，除非随后重新抛出，或者这里是隔离点：线程入口、请求处理入口、
  出错后必须先停机械臂的保护代码。隔离点必须记录错误，并用注释说明为什么在这里拦截。
- `try` 的范围尽量小。清理动作放 `finally`。
- 参数检查用条件判断加 `raise`，不用 `assert`。

### 6.8 其他

- 默认参数不用可变对象（列表、字典、集合），写 `None` 再在函数里创建。
- 避免可变的模块级状态；确有需要时名字加 `_` 前缀，并注释原因。
- 文件、套接字等资源用 `with` 管理。
- 可执行文件把逻辑放进 `main()`，文件末尾写 `if __name__ == '__main__':`。

## 7. JavaScript、HTML、CSS

- JavaScript：缩进 2 个空格；每条语句以分号结尾并独占一行；所有控制语句带花括号；
  用 `const`，需要重新赋值时用 `let`，不用 `var`；一次声明一个变量；字符串用单引号；
  比较用 `===` / `!==`；函数与变量用 `lowerCamelCase`，类用 `UpperCamelCase`，
  常量用 `CONSTANT_CASE`。
- 类、方法、具名函数前写 JSDoc（`/** ... */` 形式的说明注释），写明参数和返回值。
- HTML：缩进 2 个空格；标签和属性小写；属性值用双引号；以 `<!doctype html>` 开头；
  每个块级元素独占一行。结构、样式、行为分离：不写内联 `style`，脚本放进独立的
  `.js` 文件。
- CSS：类名用连字符分词；每个选择器、每条声明各占一行；声明以分号结尾。

## 8. C++ 与 Shell

- C++：缩进 2 个空格；类型和函数用 `PascalCase`，变量用 `snake_case`，类的数据成员
  加后缀 `_`，常量写作 `kMaxJointStepDeg`；头文件用 `#define` 保护，不用
  `#pragma once`；文件扩展名 `.cc` / `.h`；不写 `using namespace`；几乎每个函数声明
  前都要有注释，说明输入、输出和单位。
- Shell：只用 bash；文件开头写用途说明；缩进 2 个空格；变量一律写成 `"${name}"`；
  条件用 `[[ ... ]]`，命令替换用 `$(...)`；报错写到标准错误；含有其他函数的脚本
  必须有 `main` 函数并在末尾调用 `main "$@"`；超过 100 行改用 Python。

## 9. 旧代码怎么处理

1. **新文件**：从第一行起完全合规。
2. **改旧文件**：新增和改动的行、被改动的函数必须合规（`--changed` 检查的就是这个
   范围）。不要为了“看起来一致”而照旧写法续写。
3. **整文件重排**：只改排版、不改逻辑的改写单独成一次提交，不与功能改动混在一起。
   提交前用 `--same-ast` 证明改写前后程序的逻辑结构完全相同。
4. 重排的顺序和进度记录在 `HANDOFF_REPORT.md`。

## 10. 自检脚本

`tools/style_check.py` 只用 Python 标准库和 git，不修改文件，不连接任何服务。
在项目根目录运行：

| 命令 | 用途 |
| --- | --- |
| `python3 tools/style_check.py --changed` | 提交前必跑：只报告相对上次提交改动过的部分 |
| `python3 tools/style_check.py 路径...` | 检查给定的文件或目录 |
| `python3 tools/style_check.py` | 检查全部自写源码，用于了解重排进度 |
| `python3 tools/style_check.py --same-ast` | 证明相对上次提交的改动只是排版 |

- 输出每行一条：`路径:行号: 错误 [规则] 说明`，或把“错误”换成“提示”。
- “错误”必须改掉，存在错误时脚本以退出码 1 结束；“提示”由作者判断，不影响退出码。
- 脚本自身的测试：`python3 -m unittest tools.test_style_check`。
- 脚本能判断的：行宽、制表符、行尾空白、分号、同行语句、导入写法、`sys.path`、
  公开函数的文档字符串与类型标注、命名形式、可变默认参数、裸 `except`、函数与文件规模。

## 11. 机器检查不了、评审时必须看的

- 名字是否准确，读名字能否知道它是什么、单位是什么、在哪个坐标系里。
- 文档字符串是否说清了“做什么、为什么需要”，而不是把函数名翻译一遍。
- 注释是否记录了取舍和踩过的坑。
- 捕获 `Exception` 的地方是否确实是隔离点。
- 会让机械臂动作的函数是否按第 5.3 节标明。
- 测试是否走过真实流程，而不是只验证了替身。
