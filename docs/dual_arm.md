# 双臂支持

本文说明程序怎样同时管理两台机械臂：现在做到了哪一步、怎么启用 2 臂、接口怎么指定臂，以及还没做的部分。

## 叫法

| 叫法 | 程序里的编号 | 左右 | 控制器地址 | 手上相机 |
| --- | --- | --- | --- | --- |
| 1 臂 | `arm1` | 左臂 | `192.168.1.19` | D435i `405622073572` |
| 2 臂 | `arm2` | 右臂 | `192.168.1.18` | D435i `344422070678` |

1 臂是项目最初的那台。接口里不写臂的编号时一律指 1 臂，所以原有用法不变。

## 用户定下的设计决定（2026-10-08、10-09）

- 一个后端进程（8089）管两台臂。原因：MSI 的显卡只有 8 GB 显存，视觉模型装不下两份。
- 两臂共用一套坐标，之后要标定两个底座的相对位置。两底座相距约 525 毫米，在同一桌面，相对朝向待标定。
- 两臂在同一个任务里配合，允许同时运动。
- 两臂之间的互撞检查要做到“规划时逐点检查两臂连杆间距离”，不是只划分区域。
- 不开启控制器自带的碰撞检测。
- 先做双臂支持，再做可读性重构的阶段 3（拆巨型函数）。

## 现在的结构（阶段 1，2026-10-09）

```
8089 后端（一个进程）
├── 视觉：相机、找框、位姿估计 —— 目前只读 1 臂手上的相机
├── 1 臂的动作控制器 ── 1 臂的设备锁、任务记录、场景快照、方案库
├── 2 臂的动作控制器 ── 2 臂的设备锁、任务记录、场景快照、方案库
└── 接口分发：按请求里的臂编号交给对应的控制器
```

| 部分 | 位置 | 说明 |
| --- | --- | --- |
| 臂登记表 | `saydo/robot/arms.py` | 有哪些臂，每台臂的配置文件、运行记录目录和设备锁在哪 |
| 动作控制器 | `saydo/manipulation/grasp_control.py` | 每台臂一个 `GraspController`，互不共享状态 |
| 占位视觉来源 | `saydo/workbench/no_vision.py` | 还没接相机的臂用它；需要画面的操作会明确报错 |
| 接口分发 | `saydo/workbench/agent_router.py` | 每台臂一个 `AgentAPI`，由 `ArmRouter` 按臂分发 |

每台臂各有一份的东西：

| 内容 | 1 臂 | 2 臂 |
| --- | --- | --- |
| 抓取配置 | `config/grasp/trial.json` | `config/grasp/arm2.json` |
| 放置设置 | `config/grasp/placement.json` | `config/grasp/arm2_placement.json` |
| 调姿设置 | `config/grasp/reorientation.json` | `config/grasp/arm2_reorientation.json` |
| 运行记录目录 | `work/grasp/` | `work/grasp_arm2/` |
| 设备锁 | `work/grasp/robot.lock` | `work/grasp_arm2/robot.lock` |

手眼标定、工具记录和“同型号相机复用”策略的文件位置写在各臂的抓取配置里（`handeye_file`、`tool_file`、`camera_reuse_file`）。

各臂共用的东西：物品模型与夹法库（`work/object_models/`）、Agent 任务数据库（`work/agent/tasks.sqlite`）、视觉模型。修改共用数据（编辑夹法、改物品位姿模式）时要求**所有臂**都空闲。

### 为什么每台臂一把设备锁

设备锁（一个文件，谁锁住它谁才能指挥机械臂）原来只有一把，所以同一时刻只能有一个任务。现在每台臂一把，两台臂可以同时各执行一个任务；同一台臂仍然一次只做一个任务。

### 为什么场景快照和方案库也是每臂一份

快照里的物品位置是按“拍摄它的那台臂的底座”记录的，方案里的路径是按某一台臂的关节算的。两台臂的底座不在同一处，混用会让机械臂去错位置。等两底座的相对位置标定好、引入公共坐标之后，再把场景统一起来。

## 怎么启用 2 臂

8089 启动时检查 `config/grasp/arm2.json` 是否存在：存在就为 2 臂创建控制器，不存在就和以前一样只有 1 臂。这个文件只在各机器本地维护，不入 Git。

`arm2.json` 的字段与 1 臂的 `trial.json` 相同，各项都要换成 2 臂自己的：`robot_ip`、`tool_file`（2 臂的工具记录）、`handeye_file`（2 臂的手眼标定）、`camera_reuse_file`、`table_z_m`（桌面高度）、工作范围、`return_after_lift`（复位姿态）、夹爪参数。

截至 2026-10-09，MSI 上**还没有** `arm2.json`，2 臂尚未启用。启用前还缺：

| 项目 | 现状 |
| --- | --- |
| 夹爪 | 已可读（2026-10-09）：与 1 臂同型号（ZX，固件 V1.154），通信模式 115200，位置 1000 |
| 工具 | 控制器里已建 `grip_tcp`，但当前选中的仍是零偏移、零负载的 `Arm_Tip`。手眼标定期间应保持零偏移工具；标定之后切到 `grip_tcp` 并读回记录 |
| 工作坐标系 | 当前是 `World`，程序要求名为 `Base` 的零偏移坐标系 |
| 手眼标定 | 未做；采集脚本已支持指定相机与新会话，流程见 `docs/calibration.md` |
| 桌面高度、工作范围、复位姿态 | 未测、未记录 |

## 接口怎么指定臂

`/api/agent/` 下的接口用 `arm` 指定机械臂，缺省为 `arm1`。

| 请求 | 写法 |
| --- | --- |
| 查询（GET） | 查询串里写 `?arm=arm2` |
| 提交（POST） | 请求体里写 `"arm": "arm2"` |
| 带任务编号的查询或取消 | 不用写，按任务记录里的臂处理 |
| 列出各臂状态 | `GET /api/agent/arms`，返回编号、名字、左右、是否忙、持物、活动任务、是否已接入视觉 |
| 停止 | `POST /api/agent/stop`：请求体为 `{}` 时停止**全部**臂；写 `{"arm": "arm2"}` 只停该臂 |

任务编号（`request_id`）在两台臂之间共用一个数据库：同一个编号不能先后用于两台臂，否则返回 `REQUEST_ID_CONFLICT`。任务记录里新增 `arm` 字段。

停止全部臂时各臂并行发送、互不等待。有臂未确认时返回 `STOP_UNCONFIRMED`，`arms` 里写明每台臂的情况。只配置了一台臂时，停止的应答与以前完全相同。

页面上的“停止”按钮、任务执行器的停止失败兜底、服务退出，都会取消全部臂的当前任务。

## 还没做的

| 项目 | 说明 |
| --- | --- |
| 2 臂的视觉 | 8089 只读 1 臂的相机；2 臂的抓取、场景采集等需要画面的操作现在会报“尚未接入视觉” |
| 夹法绑定按臂 | 每套夹法保存时记下了当时的工具参数和手眼矩阵，使用前逐字比对。2 臂的这两项与 1 臂不同，现有夹法在 2 臂上会被拒绝，需要改成“几何共用、绑定信息每臂一份” |
| 两臂互撞检查 | **尚未实现**。逆解检查只查一台臂自身，不知道另一台臂存在 |
| 公共坐标 | 需要先完成 2 臂手眼标定和两底座相对位置标定 |
| 智能体与任务执行器 | MCP 工具、任务执行器的工具都还没有臂参数；任务执行器每轮只允许一个工具调用，两臂同时动作需要改成一轮可发两个 |
| 网页 | 页面只显示和操作 1 臂 |
| 运维脚本 | 8089 重启脚本里的相机序列号仍按 1 臂写死（视觉接入 2 臂时一并处理） |

## 安全注意

阶段 1 之后，程序在结构上已经允许两台臂同时运动，但**两臂之间没有任何互撞保护**，控制器自带的碰撞检测也按用户决定保持关闭。在互撞检查完成之前，不要让两台臂在工作范围重叠的摆位下同时执行动作。
