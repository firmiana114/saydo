# 固定试管抓放脚本

入口：`python -m scripts.fixed_pick_place`。单臂、静态场景、无LLM决策；每次运行先定位试管和试管架，再检查完整抓取/调姿/搬运/下降/松爪后退出路线。先把操作员确认的空孔按“孔口到试管当前位置的水平距离”由近到远排序（距离相同按孔位名），取第一个全程通过的候选，即最近且可行的孔位；开动后不更换孔位或目标，不自动重试失败动作。

## 运行

在MSI项目根目录执行，8089须运行新版后端。眼在手画面为640×360；试管和试管架必须同时可见且保持静止。框只用于目标分割初始化，位姿由同一份新RGB-D画面的SAM和FoundationPose重新求解。`--tube-box`和`--rack-box`均可省略：省略时由8089当前的自动检测器在同一冻结画面中给框（缺省为常驻本地Qwen3-VL，读取各物品目录的`qwen_detection.json`；以`--detector ssdlite`启动时读取`local_detection.json`走Grounding DINO；以`--detector llm`启动时调用远端模型）。自动检测必须恰好得到一个可靠候选，否则本次采集失败并提示改为传框，不会猜测。物品没有对应检测配置时须提供框；不能使用D405全局图片的坐标。

全部自动找框：

```sh
work/task_runner_env/bin/python -m scripts.fixed_pick_place --empty-rack
```

自动找框失败或有多个同类物品时手动传框，以下 `x0,y0,x1,y1` 是须替换的实际框坐标，不是可直接运行的实机参数：

```sh
work/task_runner_env/bin/python -m scripts.fixed_pick_place \
  --tube-box x0,y0,x1,y1 \
  --rack-box x0,y0,x1,y1 \
  --empty-rack
```

默认只采集和规划，不运动。`--empty-rack` 表示操作员确认全部候选孔为空；若部分孔被占用，改用 `--free-slots A01,A02,B03`。孔位名称属于估计模型坐标，未标记试管架有180度编号歧义；必须先建立物理编号对应，不能将未知编号声明为空。脚本没有自动占用检测。整架确实空闲时，此编号歧义不影响“任意空孔”的选择。

默认模型为 `transparent_test_tube_150mm`、`test_tube_rack_40_272x112x85`；可用 `--tube`、`--rack` 指定兼容模型。试管须为5D、模型+Z朝开口、-Z端为底端；试管架须有模型本地 `features.json` 中的 `<孔位>.entry` 和 `<孔位>.support`，含孔径。拒绝倒置/超过5度倾斜的架子位姿，不能用翻转目标角度掩盖错误定位。

默认将试管底端放到模型支撑面上方3毫米，再松爪，使用 `--release-gap-mm 0..5` 调整。它是模型几何目标，不代表已验证接触或稳定入孔。中部夹持可能与架体干涉，须核验实际夹指净空，不应仅凭规划通过执行。

明确要实机运行时，在相同命令增加 `--execute`。每次命令仍重新采集、规划；程序只有在整条路线通过后才提交已保存方案编号，不接受调用方临时改路径。孔位选择是确定的：同一场景重复规划得到同一孔位；更近的孔若因几何检查或路径不可行被跳过，命令输出的`nearer_slots_rejected`会列出它们，逐孔原因见任务诊断的`slot_attempts`。开始前须无活动任务、无夹持记录；软件还会核对夹爪反馈，不能把物理上仍持物但重启后记录丢失当成空爪。

Ctrl-C在执行阶段会请求现有软件停止，不松爪；停止不能确认时须现场处理。请求超时只查询原任务编号，不换编号重复发送。默认后端 `http://192.168.101.65:8089`，令牌沿用现有MCP私有文件，可用 `--base-url`、`--token-file` 指定。

## 规划怎样找到一条可行的路径，以及为什么这样排序

规划的做法是“逐个检查候选方案，取第一个全程走得通的”。候选方案由三样东西组合而成：

| 可变的东西 | 候选数 | 含义 |
| --- | --- | --- |
| 夹持方向 | 24 个，每 15 度一个 | 试管竖起来以后，夹爪从哪一侧夹着它 |
| 转移路线 | 12 条 | 直接过去，或者抬高、向侧面绕行 |
| 在哪里把试管翻成竖直 | 3 种 | 原地翻；边走边翻、到孔位正上方时翻完；走到一半时翻完。后两种只与“直接过去”搭配 |
| 孔位 | 操作员声明为空的那些 | 由近到远 |

每检查一个候选约 0.4～0.6 秒：沿整条路径做几千次逆解（由夹爪位置反算关节角），再做碰撞检查。

检查的顺序（2026-10-10 起）：

1. 先试不绕行的路线：24 个夹持方向先各试一遍“原地翻”，再各试一遍“边走边翻”，然后才轮到绕行路线。边走边翻时，试管底端始终在“当前位置到孔位正上方”的直线上，试管其余部分只在它的上方或同一高度摆动（2026-10-10 加入：原地翻不了的位置，比如紧挨着立杆，边走边翻有时可以）。
2. 同一条路线里，先单独试“夹爪转动最少”的方向：它可行时动作最短，而且只花检查一个候选的时间。
3. 其余方向按“夹爪朝外”的程度排序：终点处夹爪越是从机械臂这一侧伸出去越先试。统计 21 次成功的规划，成功的都是朝外的那几个方向；原来按编号从小到大试，每次都要先把朝里的十来个方向连同它们的 12 条路线全部试完。
4. 第一个之外的候选每批同时检查 8 个，再按上面的顺序取第一个通过的。并行只影响快慢，不影响选出哪个方案。
5. 某个夹持方向卡在调姿段（把试管翻成竖直）时，换转移路线没有用，不再试它的其他路线。全部方向都卡在调姿段时立即结束，不再换孔位：调姿在原地进行，与去哪个孔位无关。
6. 整次规划最多 60 秒，超过即放弃，不发送运动。

回放最近 16 次历史方案的放置部分（不含碰撞检查）：规划耗时的中位数由 4.7 秒降到 1.0 秒，最长由 45.7 秒降到 2.5 秒。

“边走边翻”的实测效果有限：回放里它救回了 2026-10-09 撞倒立杆那次的场景（原地翻无解，边走边翻找到离立杆 128 毫米的方案），但 2026-10-10 桌上的真实场景（试管离立杆 27 厘米）仍然 60 秒内找不到方案，失败的候选绝大多数是求不出连续的关节解。

仍然存在的问题：加入立杆的碰撞检查后，物品摆在立杆附近时，通过逆解的候选常被碰撞检查否决，而其余候选又求不出连续的关节解，整次规划会在试完全部候选后失败（8～40 秒）。原因是现在的逆解一次只给出一种手臂摆法，不会主动去找手肘避开立杆的摆法；解决办法是改用能直接指定手肘方向的解析逆解，尚未实现。

## 固定方案与执行边界

后端新增认证任务操作 `plan_fixed_pick_place`、`execute_fixed_pick_place`，用于此脚本，未加入LLM工具清单。复用现有任务幂等记录、设备锁、取消入口和反馈检查。

- 首次动作前检查预抓、接近、夹持后抬升、先调姿、保持朝向搬运、预放置、竖直下降以及松爪后沿Base +Z退出50毫米；预放置高度沿用配置，缺省100毫米。
- 抓取与放置采样联合求解，包含下降和退出；不是只验证几个终点。最多480个采样点。孔位及每孔的有限路径候选不设总墙钟时限，客户端等待到结束或取消；单次逆解仍有防卡死预算。候选耗尽只代表当前搜索没找到，不能断言所有孔物理不可达。
- 方案存储固定TCP航点和规划时的关节构型，绑定场景、起点、配置、夹法/模型，5分钟过期、进程重启失效、一次性领取。发出第一个动作前全程再核验，此时关节构型须与规划一致，否则拒绝。TCP航点、孔位和各段顺序在执行中不更换。
- 抓取后的实际夹持关系与预测偏差超过2毫米/2度即停止，不临时重规划放置。搬运和下降仍由原反馈监测保护。
- “固定路径”指固定命令航点及其采样点的关节解。七关节臂同一位姿有无穷多组关节角，控制器执行movel时自行解算冗余，实测下降40毫米后关节角与离线解相差10至35度，使离线验证失去意义。因此固定流程**不发送movel**：直线段按离线采样点（间距约10毫米）逐点发送movej，每点到位后核对实际关节角与所发关节角相差不超过0.5度，整段结束再按位姿容差核验。离线估算相邻采样点之间夹爪偏离直线不超过约0.25毫米（入孔下降段约0.04毫米）；这是按关节线性插值的估算，不是实测轨迹。每段动作前仍从真实关节反馈出发对剩余整条路径（含下降与退出）重新求解，找不到连续解则停止。运动呈逐点停顿，整个抓放需数分钟：固定放置阶段的总时限为600秒，命令行等待执行结果的时限为900秒。每段的关节运动次数与终点关节角记入任务诊断的`sampled_joint_segments`；重解结果与规划值相差超过0.5度时记入`joint_configuration_changes`。网页普通抓取、SayDo任务和通用持物运动不受影响，仍使用控制器movel。
- 检查范围沿用机械臂采样自碰撞、IK/FK、工作区、物品/桌面范围。**尚无完整夹指/架体/另一机械臂碰撞和插入力控，也不证明孔空闲或松爪后稳定。** 默认仅规划，未进行实机抓放验收。

运行记录保存在 `work/fixed_pick_place/<运行ID>/`，包含请求、场景、固定方案及执行结果；后端诊断存于 `work/grasp/object_motion_jobs/`，固定方案沿用 `object_motion_plans.sqlite`。模型、夹法和特征仍读取各 `work/object_models/<物品ID>/`，不建立跨物品的集中配置。

固定流程只读规划期间按Ctrl-C会按原任务编号请求取消规划，不发送机器人停止/松爪命令；只取消仍属于该编号的只读任务。执行期间Ctrl-C仍走原软件停止。取消检查在候选之间及单次逆解返回后进行。无总时限不取消场景过期、配置/起点/夹持版本核验。
