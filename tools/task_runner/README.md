# Saydo 自然语言任务执行器

一个 Python 编排进程通过 Responses API 完成“观察 → 选择工具 → 等待结果 → 再判断”的任务循环。已有 MCP、视觉算法、夹法参数和机械臂后端保持独立；执行器复用 `tools/robot_agent/client.py` 的认证 HTTP 客户端，不通过 Codex，不执行模型生成的代码。

## 运行

需要 Python 3.11+。从项目根目录执行：

```sh
python3 -m venv work/task_runner_env
work/task_runner_env/bin/python -m pip install -r tools/task_runner/requirements.txt
cp .env.example .env
chmod 600 .env
# 在本机编辑 .env，填写模型密钥、后端地址及后端令牌路径。
work/task_runner_env/bin/python -m tools.task_runner.api
```

已有 `.env` 时保留并修改，不要用示例覆盖。`.env` 由 Git 忽略，安装及同步必须单独提供；密钥不进入网页或普通日志。模型密钥与机械臂 MCP 后端令牌分开。`.env` 支持 `KEY=value`、JSON 双引号或单引号，不执行 shell 展开。可用 `--env` 指定另一文件。

默认模型为 `gpt-6-sol`，推理强度为 `medium`，不自动切回其他模型。`SAYDO_LLM_FALLBACK_MODEL` 默认留空；只有管理员显式填写时，才会在第一次模型决策收到明确“模型不可用”响应后回退。认证失败、限流和网络错误不改变模型，任务开始调用工具后不切换模型。

`SAYDO_LLM_PROXY` 可选，只影响模型 HTTPS 请求。MSI 当前使用已有的本机代理 `http://127.0.0.1:7897`；模型代理与机械臂 HTTP 连接分开，后者不读取系统代理。该端口是当前机器配置，其他机器需按实际情况填写。

`SAYDO_RUNNER_MODE` 支持：

- `read_only`：只向模型提供观察、查询和结束工具。
- `preview`：另允许目标选择、初始化及方案预览；不把真实动作替换成伪造成功的预览。
- `execute`：允许抓取、姿态调整、放置、复位和模型主动停止；仍要求用户任务包含对应动作意图，且后端自身也允许执行。

默认 `execute`，未填写模式时也采用执行模式；需要限制为只读或预览时显式配置。切换模式须编辑本机 `.env` 并在任务结束后重启执行器；网页和模型不能更改模式。服务启动不会自动提交任务或发送动作。任务界面集成在 **8089 工作台的第5页「SayDo 任务执行器」**。8089 仅向固定的 `127.0.0.1:8091` 转接任务界面和 API；独立编排进程仍使用上述启动命令，8089 启动不会代为启动它。原四页及未保存草稿保持独立。右侧“停止运动”同时取消自然语言任务，模型返回迟到结果时不会继续动作。任务服务不可达时仍尝试原机械臂停止，并明确报告任务停止未确认。

MSI 局域网入口为 `http://192.168.101.65:8089`。也可从 Mac 转发访问：

```sh
ssh -N -L 18889:192.168.101.65:8089 msi
```

浏览器打开 `http://127.0.0.1:18889`，选择第5页。独立诊断页面 `http://127.0.0.1:8091` 仍可使用。

## 模块与接口

- `llm_client.py`：仅发送原生函数定义和本次任务历史，保留模型可回传的 output；图片作为 `input_image`，不塞入普通 Base64 文本。禁用服务端存储、流式和并行工具调用。
- `tool_registry.py`：22 个业务工具加本地 `finish_task`（共23个），严格校验类型和多余字段。发送给提供方的函数定义使用受支持的 JSON Schema 子集；长度、唯一性和几何范围等约束仍在本地校验，不因接口兼容而放宽。原 `get_task` 留在程序内部；MCP 共24个工具，其中 `get_task` 由执行器内部轮询，候选图片由选择流程内部读取；执行器额外提供本地 `finish_task`。
- `robot_adapter.py`：复用原认证客户端，等待模型加载、跟踪和后端任务。发生提交超时时按原编号查询，不自动重发，不替换放置的夹持或配置版本。
- `runner.py`：单任务、串行工具，最多20轮、整任务600秒；动作等待120秒、跟踪等待45秒、轮询间隔0.5秒。限制本次上下文为2 MiB，不加入长期记忆或自动续跑。相同动作已成功时禁止换调用编号重复执行。
- `store.py`：`work/task_runner/runs.sqlite` 保存任务、调用映射、确定参数、阶段、结果、耗时和回退事件；发起请求前写入请求编号。完整原始运动报告仍保存在已有后端。
- `api.py`：任务页和同源 API；只绑定回环地址，拒绝异常 Host、跨站 POST 和非 JSON 写入。状态目录设备锁阻止重复启动。

```text
POST /api/task-runs                    {"instruction":"..."}
GET  /api/task-runs                    最近20次任务与执行模式
GET  /api/task-runs/{run_id}            阶段、工具调用与最终结果
POST /api/task-runs/{run_id}/cancel     {}
POST /api/task-runs/stop                {}，工作台全局停止
```

取消按钮明确表示“停止机械臂并取消”：绕过 LLM，禁止后续调用，立即发软件停止；若有已发出的写请求尚未返回，等待其结束后再次确认停止，防止迟到的提交越过第一次停止。**即使只读/预览任务，用户点击此按钮也会发软件停止**，不会松爪。正常只读任务超时或进程退出不会自动向空闲机械臂发停止。

`finish_task` 的 `succeeded` 必须引用本轮全部真实成功动作，并在结束前核对后端状态；`answered` 只表示已回答问题或解释预览，不表示实际操作完成。页面显示“已核验的动作”，与模型给出的说明区分。控制器完成仍不能独立证明接触桌面、无滑动或长期放置稳定。

姿态工具 `preview_reorient` / `reorient` 沿用 [MCP 参数约定](../robot_agent/README.md#姿态调整参数)，其中 `request_id` 由执行器生成。执行器等待任务后核对同一夹持身份、版本递增及实际朝向误差；预览不递增版本。成功结果提供新版本供后续放置使用；失败、中断、版本不一致或朝向误差超限时不继续动作。

通用持物链路使用 `plan_held_object_motion` / `plan_release` 生成方案，再用 `execute_plan` 执行。另提供 `get_object_geometry` 和 `get_task_diagnostics`；详见 [目标参数与执行边界](../foundationpose/OBJECT_MOTION.md)。规划失败以PLAN_FAILED证据交回模型，可在用户目标范围内更换路点重新规划；真实执行失败、结果未知或到位核验失败仍阻断后续动作。执行器核对物品参考点位置、朝向、夹持版本及松爪/退出结果，重启后不会重放未确认方案。preview模式允许生成方案，execute_plan只在execute模式开放。

## 前端模型与推理强度

第5页新任务表单可选择 `gpt-5.5`、`gpt-6-luna`、`gpt-6-sol`、`gpt-6-astra`，推理强度可选 `low`、`medium`、`high`。默认仍取服务器配置（Sol/medium）；浏览器记住上次选择，轮询不会覆盖草稿。选项只影响下一次提交，运行期间控件禁用。

2026-09-28 当前提供方实测支持6-Sol和6-Luna的工具调用、图像及工具结果续答；6-Terra未在提供方清单中，实际请求返回模型不可用，暂不开放。浏览器保存的5.6-Sol/Terra选择迁移为6-Sol，5.6-Luna迁移为6-Luna，保留推理强度；历史任务记录不回写。目标识别独立固定为6-Sol/low：本次6项真实场景框选测试中Sol全部在20秒内返回并通过粗框检查，Luna两项超时；不把小样本测试等同于长期准确率。

`POST /api/task-runs` 可额外携带 `model` 和 `reasoning_effort`，后端按白名单校验。省略时兼容旧客户端，使用服务器默认；显式选择模型时不自动回退到其他模型。创建任务时固定模型、强度及回退策略，每轮HTTP请求使用该任务的强度，历史记录与每次LLM时间线也记录这些值。不会修改 `.env` 或返回密钥。提供方不接受某组合时任务明确报错，不静默替换。

“最近任务”和“执行进度”各自有独立滚动区域。进度停留底部时跟随新消息；向上阅读时保留位置。历史列表内容没有变化时不重建，状态变化时也保留滚动位置。

## 模型请求诊断与上下文

新任务每轮 `events[].diagnostics` 记录模型/强度、请求字节数、输入/工具定义大小、图片数量、连接/TLS/上传阶段、响应头与首字节时间、HTTP状态、合法格式的提供方request ID、返回字节数、总耗时和具体异常类型。成功响应另保留输入/输出/缓存/推理token数；缺失值不填零。时间均为该轮开始后的秒数；有代理时TCP连接耗时通常指连接本机代理，不代表直达提供方。非流式请求等待响应头的时间可能包含网络、排队和生成，不能直接称为纯推理耗时。

诊断随既有 `work/task_runner/runs.sqlite` 的任务事件持久化，执行中更新 `llm_started.diagnostics`，结束写入对应 `llm.diagnostics`；前端显示阶段、请求大小、上传/首字节时间及异常类型。传输事件每轮最多48条；不保存原始请求/响应正文、错误消息正文、图片内容、密钥、URL或完整HTTP头。旧任务不补造缺失数据。90秒请求时限及不自动重试规则保持不变。

模型上下文与任务日志分开：成功且已核验的抓取结果仅保留当前夹持变换/版本、有效夹法参数和任务证据，省略历史路径、候选及重复状态方案；相同夹持记录只保留一份并注明引用。初始/状态快照中的已完成历史方案也省略。待执行规划、失败证据、显式诊断读取及原动作核验保持完整，原有任务日志和后端报告保留供查询。此精简不改变物理执行或缩减核验步骤。

## 执行信息流

第5页的“执行进度”按记录顺序显示：LLM调用及耗时、模型过程说明、工具开始/完成与必要的阶段更新，最后完整显示总结。LLM耗时指一次模型API请求从发出到收到完整响应的总时间，包含网络等待；失败、取消和初次回退的每个请求分别计时。等待期间显示已用时间，完成后保留最终耗时。

过程说明来自模型的公开文字或函数参数 `progress_message`（同一轮优先使用公开文字，避免重复）；它描述已确认进展和下一步操作，不展示内部推理或加密推理内容。该字段只用于显示，参数校验后即从设备工具入参中移除，不改变后端动作接口，也不额外发起LLM请求。当前仍是非流式模型请求，每轮响应到达后更新说明，页面每秒查询进度。

时间线带时间戳和递增序号，保存在运行记录中；最终总结只在证据检查结束后展示一次，不截断。页面更新等待计时不会重建之前的文字。旧任务缺少过程说明时明确标为历史记录，仅展示已有耗时、工具结果和总结，不补造当时的文字。

## 故障与恢复

后端未确认的动作、未确认停止会阻断新任务。重启不续跑；尚在提交/执行中的真实动作记录会标为结果未知。只读任务中断不形成机械臂动作未知记录。

操作员实际核对现场及原任务记录后，先停止执行器，再显式运行只读核对工具：

```sh
work/task_runner_env/bin/python -m tools.task_runner.reconcile \
  --run-id <运行编号> --confirm-scene-inspected
```

该工具要求后端空闲且停止已确认；查询已记录的任务编号，不发送动作、不恢复旧任务。仅当操作员确定原请求未提交且后端查无该编号时，额外使用 `--confirm-request-not-submitted`。核对后重新启动执行器，再提交新指令。不要直接删除数据库来绕过未知结果。

## 验证

```sh
# 不连接设备的单元/集成测试
work/task_runner_env/bin/python -m unittest discover -s tools/task_runner -t . -p 'test_*.py' -v
# 使用 .env 密钥；仅发送合成测试图片和无害的假工具，不连接机械臂
work/task_runner_env/bin/python -m tools.task_runner.probe
```

`probe` 使用 `fixtures/color_halves.jpg`（640×360 JPEG，左红右蓝）和随机校验码，检查严格函数调用、回传完整模型输出、工具结果续答、图片输入及初始模型回退，摘要保存到 `work/task_runner_validation/provider_probe.json`。先完成这些检查，再做真实查询和方案预览；真实抓放需另外进行现场验收。
